## 3. What changed

`worker/snapshot.js` is now the single reader. Every snapshot read in index.js and in every module goes through `readSnapshot(env, cls)`. `fetchSnapshot` is gone from index.js.

- **Per-isolate memo**, then **KV `snapcache`**, then **one fetch at a time per isolate** (single-flight). The tick's 2–4 simultaneous reads become 1.
- **Max age per class.** guest, dashboard, send, dial, ops, brain and background all use **300 s** and share one copy. `write` (read-modify-write by row index) does a real read every time. `probe` (brain `snapshot_retry`) accepts only a real answer. **Screens never force a read.**
- **Seeing your own write:**
  - `sheetBatchWrite` patches the written cells into the memo and into a small KV overlay `snappatch` (last 15 min). Every reader in every isolate applies it, so nobody pays a fetch to see a write that just happened.
  - A `call_result` patches rsvp (P) and party (Q) by guest_id. It also bumps `snapdirty:act`, so the dialer and senders refetch: tries and call_status are computed inside Make.
  - Any other write that touches the snapshot tabs bumps `snapdirty`. Every class except ops/brain/background refetches once.
  - Patches are applied only when they are newer than the fetch's *start* time.
- **Make down:**
  - A failed read (including a paused scenario's `200 Accepted`) backs off **60 s for every caller** (`snapfail`).
  - Readers then get the newest of memo / `snapcache` / **`snaplast` (7 days)**, tagged stale. The client dashboard and the admin "biz" view return `stale_since`, and `/api/ops/realtime` returns `make`.
  - **send/dial never get a copy older than 15 min.** They return null and `snapWhy(env)` = `snapshot-stale`. Senders and the dialer skip with `why: 'snapshot-stale'`: `runShirDispatch`, `runShirCallbacks`, `drainCallRounds`, `drainPartyNudges`, `drainLateInvites`, `runEventDayBlasts`, `runDailyEngine`, `resendInvitation`, `handleGiftBlast`, `/api/wave-retry`, and the pacer autoretry.
  - These used to treat an empty read as "nothing there", with real consequences:
    - Late invites and party nudges were **deleted** as "guest/event not found".
    - Call rounds were marked **done with 0 guests**.
    - Event-day blasts raised a "cancelled" alert.
    - Callbacks rang a guest from Noa's number as an "unknown" caller.
- **Write outbox:**
  - A failed `sheetBatchWrite` is stored as `sheetq:e:<ts13>:<rand>` (7 days), and `sheetq:pending` is set.
  - While a queue exists, a new write first tries an inline drain (10). If the queue is still not empty, the new write goes **behind** it, so an old value can never land on top of a newer one.
  - The pacer step `sheet_outbox` replays the queue oldest first, 25 per tick, and stops at the first failure.
  - After a write failure, writers back off 60 s.
  - `sheetq:pending` is cleared only when `list()` is empty **and** the last enqueue is older than 90 s, because `list()` lags its own writes.
  - The queue length shows in `/api/ops/realtime` → `make.outbox` and in the brain finding.
- **Brain `make_down`.** P1 when the reader or writer is failing on **2 brain ticks in a row**. Hebrew title "Make מושהה/לא עונה — קריאה וכתיבה לגיליון לא עובדות", with the outbox size in the detail. It uses **Slack gate key `make_down`**: findings can now carry `slack_key`, which runBrain uses for the alert and for `resolveSlack`. So it posts once and closes once.
- Registry: node `sheet_outbox` (pacer step), `make_down` added to `brain_health.checks`, and `registry-code.json` regenerated.

**The ≥90% goal is not met within the brief's 120–300 s limit.** The floor is the pacer itself: senders and the dialer read every 10-minute tick, and a 300 s max age means every tick is a miss (144/day). The admin board polling every 60 s, which caused most of the burn, is now absorbed. Options to go further (each is Richard's call, none is done):
1. Raise the max age to 900 s for ops/brain/background/guest/dashboard and 600 s for send/dial. Own writes stay correct through patches and dirty markers. Estimate ~130 reads/day (−84%).
2. Stop reading the whole sheet. Make the Worker own a copy (D1 or KV), written by the same writes that go to the sheet, with a nightly full sync. That would cut ~95%+, but it is a separate project.
3. Find out where the other ~4,600 credits/day go (the 34 other scenarios).

## 5. Before switching Make back on

- **Clear the webhook queue of `3 · נתוני דשבורד` (6959463).** A paused scenario's webhook still accepts calls and **queues** them, then runs every one at full price when it is reactivated. Those queued reads are worthless. The new 60 s backoff only limits how fast the queue grows after this deploy.
- `TEST - ishur sheets reader` (7150125) queue: it holds writes too. The outbox replays every failed `sheetBatchWrite`, and those writes are absolute cell values, so a second replay is harmless. Direct appends (logs, seating) are **not** in the outbox. Look at the queue before you purge it.

## 6. Not covered / known edges

- KV is eventually consistent across locations (up to ~60 s). A dirty marker or patch written in one PoP can reach another PoP late. Inside one isolate it is exact.
- The `snappatch` overlay is read-modify-write on one key. Two isolates writing in the same second can lose one patch. A failed `put` falls back to dirty, but a silently overwritten one does not. The cell then catches up within ≤300 s.
- Only `sheetBatchWrite` is queued. Direct BRAIN_HOOK writes (seating, send date, appends, `setBrainActive`) still fail loudly as before.
- Make may also have the original call queued (see §5), so a replayed write can land twice. That is harmless for batchUpdate.
- The after-numbers are a model on top of one measured day (03/11), not a measurement.
- `node worker/scripts/check-registry.mjs` (line-number evidence) already failed on `integ-2026-11-02` before this change. It is not part of the test suite and was not fixed here.
