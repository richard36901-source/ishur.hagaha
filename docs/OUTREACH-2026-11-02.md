## How it works

**Venues** live in KV as `venue:<id>`; id = 12-hex FNV hash of
`email|whatsapp`, so re-importing the same CSV updates rather than
duplicates. `venueph:<972…>` and `venueem:<email>` point back to the id for
reply lookup. WhatsApp number = the one marked "(WhatsApp)" in the CSV, else
the first 05x mobile; landlines and the ad call-tracking numbers are not used.

**Pacing and window** (`planBatch`, pure): email 10/day for the first 7
calendar days after the first real send, then 20/day; WhatsApp 15/day. Window
Sun–Thu 10:00–16:00 Israel for both; WhatsApp additionally requires
`sendWindowState()` from shir.js. Skipped: status in sent/replied/optout/
bounced, no address for the channel, already has a successful `out:` record.
A venue whose last send *errored* is planned again. **Note:** a venue that was
emailed has status `sent` and is therefore skipped by the WhatsApp plan (and
vice versa) — one channel per venue, as the spec said. If Richard wants both
channels per venue, change `SKIP_STATUS` to drop `sent` and rely on the
per-channel `out:` record (one-line change, tests cover the record check).

**A/B**: subject A = `{venue}`, B = `{venue} — מספר סופי לכל אירוע`. Sticky
assignment by `hashUnit('outreach|' + id)` from ab.js. Body has one variant;
`SUBJECT`/`BODY`-style map means a second body is a one-entry addition.

**Send** (`action:'send'`, `dry:false`) runs only when
`env.OUTREACH_ENABLED === 'on'`; otherwise it returns the plan with
`error:'outreach-off'`. Also refused: outside window, daily cap reached,
WhatsApp template not `APPROVED` (checked live on the client WABA
1060242146337688 with `clientToken(env)`, cached 10 min in `outreach:tmpl`).
Email goes through `env.EMAIL.send({to, from, replyTo, subject, html, text,
headers:{'List-Unsubscribe': mailto}})`. WhatsApp goes through
`sendTemplate(env, phone, 'ishur_venue_intro', [venueName], '', 'he', 'client')`
— Noa's number. Every send writes `out:<id>:<channel>` {variant, at, subject,
message_id}, sets the venue status to `sent`, bumps `outreach:day:<ch>:<date>`,
and logs an audit row `kind:'outreach'`.

**Email failures degrade, never crash**: missing binding →
`email-binding-missing`; `E_SENDER_NOT_VERIFIED` / `E_SENDER_DOMAIN_NOT_AVAILABLE`
→ `email-domain-not-enabled` and the batch **stops** (every further send
would fail the same way); venue stays `new` and is planned again next time.
`E_RECIPIENT_SUPPRESSED`/`E_DELIVERY_FAILED` → venue `bounced`.

**Tracking**: `GET /px/<token>.gif` marks `opened_at` once (1×1 gif, no key);
`GET /r/<token>?u=<url>` marks `clicked_at` (+ `clicks`) and 302s only to
`https://*.ishur.io` or `https://wa.me`. Token = `o|c` + id + `.` +
HMAC-SHA256(secret, `kind|id`)[0:20]; secret = `OUTREACH_SECRET` or
`ADMIN_KEY`. Open tokens do not work as click tokens. Links in the mail: the
partners page (`https://ishur.io/partners.html?utm_source=outreach&utm_medium=email&utm_campaign=venues`,
page not built yet — fine) and `wa.me/972559504499`, both via `/r/`. Tracking
host is `go.ishur.io` (`OUTREACH_TRACK_BASE` overrides).

**Stats** (`action:'stats'` and inside `list`): per channel × variant: sent,
opened, clicked, replied, optout, bounced, failed; `leading` = the subject
with the best reply rate (then open rate), shown as the gold tile on the board.

returns `null` when `from` is not a venue (normal flow continues), else
