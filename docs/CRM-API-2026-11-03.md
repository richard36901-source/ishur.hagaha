# ishur.io CRM API (03/11/2026)

Backend for the CRM screens of `ops.html`: Phase 3 §7 of `docs/OPS-CENTER-PLAN-2026-11-03.md`.
Code: `worker/crm.js` (routes, pure logic, hooks) and `worker/store.js` (repository). Migration: `worker/migrations/0003_crm.sql`.
**Field names here are the contract.** Add fields freely; never rename or remove one without changing this doc in the same commit.

The examples come from a run against the stubbed fixture (same stubs as `worker/test/crm.test.mjs`). They are real response shapes with fake data. Long objects are cut with `…`.

## Auth and errors

Same as `/api/ops/*` (see `docs/OPS-API-2026-11-03.md`): `X-Admin-Key` or `Authorization: Bearer` on GET, `{"admin_key": …}` in a POST body, admin session stamps work too. Never put the key in a URL.

`403 {"ok":false,"error":"bad-admin-key"}` · `404 {"ok":false,"error":"unknown-crm-route","routes":[…]}` · `404 {"ok":false,"error":"not-found"}` · `400 {"ok":false,"error":"bad-…"}` · `500 {"ok":false,"error":"crm-failed","why":"…"}`.

## Storage

`store.js` picks the backend per request: D1 (`OPS_DB`) when it is bound, otherwise KV (`RATE`). Both run the same `list` code, so the responses are identical. Every list response carries `store: "kv" | "d1"`. `CRM_STORE=kv` forces KV even when D1 is bound.

KV keys: `crm:t:<table>` (one doc per table; imports write it once per call through `upsertMany`), `crm:n:<type>:<id>` (notes), `crm:a:<type>:<id>` (activities, newest 500). KV is last-write-wins per doc, so two writes to the same table in the same instant can drop one. D1 does not have this problem.


### POST /api/crm/leads/import

Upserts by phone. Each source is read once and nothing is written to the source:
- `kv`: `lead:<phone>` (website and WhatsApp leads, 45-day TTL).
- `leadx`: `leadx:<phone>` (leads.html state: Monday status and owner, notes, followup becomes `next_action_at`).
- `meta`: `pullMetaFormLeads({dry:true})` over the last 60 days. Dry mode writes nothing: no `mlead:`, no Slack, no sheet.
- `monday`: board 18432553641, read-only. Columns: name, phone, status, owner, notes (`long_text_mm7gh65j`), count.

Merge rules (`importMerge`):
- Imports only fill blank fields.
- `created_at` can only move earlier.
- `status` can only move forward (`new < talking < quoted < lost/not_relevant < closed`), and never after `status_by_ops` is set.
- `source` keeps the first source seen.
- Notes are deduped by text. Monday notes are stamped no later than the lead itself, so they sort first.
- A phone that has `client:<phone>` gets `status:"closed"`.

Batched and resumable (fixed 03/11: the old import re-wrote the `crm:t:leads` doc once per lead and failed with `KV PUT failed: 429 Too Many Requests`, since KV allows about one write per second per key):
- Phones are processed in sorted order, `limit` per call (default 250, max 2000). `next_cursor` is `null` when done; otherwise send it back as `cursor` to continue. `done` says the same.
- Leads are merged in memory against one read of the table and written with **one** `upsertMany` (one KV PUT per call). Rows that did not change are not written (`unchanged`).
- Notes are deduped by text and written per lead in chunks of 20 with a 250 ms pause between chunks.
- Running the same import again is a no-op: 0 created, 0 updated, 0 notes, no table write.
- The lazy sync on `GET /leads` uses the same code and keeps its place in KV `crm:kvsync_cursor`.

```json
{"ok":true,"dry":false,"store":"kv","sources":{"kv":2,"leadx":1,"meta":2,"monday":2},"created":3,"updated":1,"notes_added":3,"skipped_clients":1,"errors":[],
 "phones":3,"processed":3,"unchanged":0,"next_cursor":null,"done":true,"writes":{"leads":1,"note_keys":1}}
```

Monday label mapping, both ways:

| Monday | ops | ops → Monday |
|---|---|---|
| חדש, לא ענה (+tag `לא ענה`) | new | חדש |
| שיחה חוזרת, בטיפול | talking | שיחה חוזרת |
| נשלח פרטים | quoted | נשלח פרטים |
| סגר | closed | סגר |
| סגר במקום אחר | lost | סגר במקום אחר |
| לא רלוונטי | not_relevant | לא רלוונטי |

### Monday sync (ops → Monday, one way)

The `CRM_MONDAY_SYNC` flag is on by default; `"off"` stops every write. These write to Monday:
- a status change: the `status` label.
- a lead note (unless the note was posted with `monday:false`): appended to `הערות`, never replacing what is there.
- a WhatsApp send that moved the status: the status plus the quote line.

Only leads with a `monday_item_id` are synced. Leads get one from `leadx` or the Monday import. Monday never writes back into the CRM, except through an explicit `POST /leads/import`.

### POST /api/crm/leads/:id/send

`{text, confirm?: true, who?}`. The checks run in this order:
1. **24h window.** The last inbound is the later of `lead.last_inbound_at` and `conv:<phone>.last_in_ts`. If there is none, or it is 24 hours old or more, the response is `{ok:false, error:"needs_template", last_inbound_at, why, templates:[…]}` and nothing is sent.
2. **Quiet hours.** Between 21:00 and 09:00 Israel time, and on Shabbat, the response is `{ok:false, error:"quiet-hours"}` (memory rule: no WhatsApp to clients or leads at night).
3. **Confirm.** Without `confirm:true` the response is a preview: `{ok:true, preview:true, confirm_required:true, to:"050*****567", text, window_closes_at}`. Nothing is sent. The UI shows it and asks again (Richard's explicit-send rule).
4. **Send.** With `confirm:true`, Noa (`sendText(..., 'client')`) sends it as free text. The send itself writes the `wa_out` activity through the hook in `whatsapp.js post()`. The status changes `new|talking → quoted` when the lead has a quote, and `new → talking` when it does not.

```json
{"ok":false,"error":"needs_template","last_inbound_at":null,"why":"הליד לא כתב לנו אף פעם: מותר לשלוח רק תבנית מאושרת",
 "templates":[{"name":"ishur_lo_siyem","he":"לא סיימת להזמין (תזכורת ראשונה)","category":"marketing"},{"name":"ishur_lo_siyem_2","he":"לא סיימת להזמין (יום אחרי)","category":"marketing"},{"name":"ishur_lo_siyem_3","he":"טיפ + הזמנה לחזור","category":"marketing"}]}
```
```json
{"ok":true,"preview":true,"confirm_required":true,"to":"050*****567","text":"היי דנה","window_closes_at":"2026-11-04T14:40:45.858Z"}
```
```json
{"ok":true,"sent":true,"wamid":"wamid.…","lead":{…,"status":"quoted"},"monday":{…}}
```
A send that failed returns `{ok:false, error:"send-failed", why}`. The templates are listed but there is no template-send route yet. Templates still go out through the existing tools.

### Payment closes the lead

`processGrowPayment` calls `crmOnPaid` right after the add-ons are granted. It finds the lead by `quote_id` from the IPN's `q:<id>`, and falls back to the payer's phone. If neither finds a lead, it creates one.
- The lead gets `status:"closed"`, `client_token`, `closed_at`, `paid_sum` and a `payment` activity. The activity id is `pay:<ref>`, so a replayed IPN does not add a second one.
- The client row `clients/<token>` gets `{phone, name, lead_id}`.
- Simulated IPNs get the tag `בדיקה`.

## Activity hooks (every message on 4499)

- Inbound on 4499 (`ch:'client'`, not an `x4499` guest): a `wa_in` activity and `last_inbound_at`. A number that is neither a lead nor a client becomes a `whatsapp` lead.
- Outbound from the Worker on the client channel (`post()` in whatsapp.js): a `wa_out` activity (`meta.template`, `meta.ok`) and `last_outbound_at`. Outbound messages never create a lead.
- Replies Richard types on the phone (smb echo, not the app's away message): a `wa_out` activity with `meta.who:"phone"`.

### GET /api/crm/clients/:token

`client` (as above, with `counts.delivered` filled in) plus a `timeline`, newest first. Each entry is `{at, kind, text, …, source}`:
- `kind`: `send · reply · payment · call · event` (from the audit log, last 60 days, max 3000 rows), `note` (client and event notes, with `pinned` and `author`), `design` (design flow history), `hostess` (assignments), and the CRM activity kinds.

## Hostesses

- **Roster row:** `{id, name, phone, city, rate, active, monday_item_id?, created_at, updated_at}`. The id is `H<phone>` when there is a phone, otherwise generated. To deactivate, send `{active:false}`. Delete needs `confirm`.
- **Assignment:** `{id, hostess_id, hostess_name, event_token, date, start?, end?, hours?, pay?, status: proposed|confirmed|done|paid, note?}`.
- **Conflict:** the same hostess, the same date, and overlapping `start`/`end` (`HH:MM`). A row without hours blocks the whole day. Back-to-back shifts are fine.
  - A create, or a move to another hostess, date or time, that conflicts returns `409 {"ok":false,"error":"conflict","conflicts":[…]}`. `force:true` saves it anyway.
  - A status or pay edit on an existing row is never blocked.

```json
{"ok":true,"created":true,"assignment":{"id":"Smw0sp44t90bd5a331f","hostess_id":"H972503333333","event_token":"c1c5fcf5-…","date":"2026-11-20","start":"18:00","end":"23:00","hours":5,"pay":450,"status":"proposed","hostess_name":"מיה לוי",…},"conflicts":[]}
```

## Notes and reminders

- **Note:** `{id, entity_type, entity_id, text, author, pinned, at, origin}`. `origin` is `monday · leadx · meta · import`, or `""` for a note typed in the ops center. Each note also writes a `note` activity.
- **Reminder:** `{id, entity_type, entity_id, due_at, text, owner, done, done_at?}`.
  - On a lead, the earliest open reminder becomes `next_action_at` / `next_action_text`. Marking it done moves the next action to the following open reminder, or clears it.
- **Brain check `crm_overdue`** (every 30 minutes): fires on open reminders and lead next actions that are past due. Severity is `P3`, and `P2` once the oldest is more than 24 hours late.

### GET /api/crm/agenda?day=

Returns what is due on that Israel day. When the day is today, it also returns everything overdue, and overdue items come first. Item `kind`:
- `reminder`
- `lead_action`: a next action that is not already listed as a reminder.
- `hostess_shift`
- `event`: events on that day, from the clients merge (skip with `events=0`).

```json
{"ok":true,"day":"2026-11-04","items":[{"kind":"reminder","id":"Rmw0sp44j05c6b133de","at":"2026-11-04T08:00:00.000Z","overdue":false,"entity_type":"lead","entity_id":"L972501234567","text":"לחזור לדנה","owner":"שלו"}],"counts":{"total":1,"overdue":0}}
```

## GET /api/crm/stats?range=

The default `group` follows the range: up to 31 days is `day`, up to 120 is `week` (weeks start Sunday), longer is `month`.
- `revenue[]`: from Grow `pay` audit rows (`closedFromPay`, one per receipt, ishur packages only).
- `funnel`: leads created inside the range. `conversion_pct` = closed / total.
- `avg_close_days`: average of `closed_at − created_at`.
- `volume[]`: `wa_out` rows count as sends, Shir `call` rows as calls, and `failed` = refused plus async-failed.
- `failures.by_code`: keyed by Meta error code.

```json
{"ok":true,"at":"…","range":{"from":"2026-10-28","to":"2026-11-03","days":7,"group":"day"},
 "revenue":[{"bucket":"2026-10-28","revenue":0,"orders":0},…],"revenue_total":0,
 "funnel":{"total":1,"by_status":{"new":0,"talking":1,"quoted":0,"closed":0,"not_relevant":0,"lost":0},"conversion_pct":0,"quoted_or_beyond":1},
```
