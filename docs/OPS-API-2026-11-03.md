# ishur.io Ops Center API (03/11/2026)

Backend for `ops.html`: Phase 0 and Phase 1 of `docs/OPS-CENTER-PLAN-2026-11-03.md`.
Code lives in `worker/ops.js` (routes and pure logic), `worker/ops-run.js` (runs ledger and kill switches) and `worker/automations-registry.js` (registry and ops metadata).
**Field names here are the contract.** The frontend builds from this file. Add fields freely, but never rename or remove one without changing this doc in the same commit.

The examples below come from the stubbed test fixture (`worker/test/ops-routes.test.mjs` setup, generated 03/11). They are real response shapes with fake data. A few values in the realtime example were filled in by hand to show non-empty fields. Long arrays are cut with `…`.

## Auth

Every route is admin-only and accepts any of these:

| How | Example |
|---|---|
| Header (GET) | `X-Admin-Key: <ADMIN_KEY or ADMIN_KEY2 or sess.… stamp>` |
| Header (GET) | `Authorization: Bearer <same>` |
| POST body | `{"admin_key": "<same>", …}` (every GET route also accepts POST with a body) |

An admin session stamp (`sess.<32hex>.<32hex>`, or the older `sess.<48hex>`) is accepted wherever the raw key is. CORS allows `X-Admin-Key` and `Authorization` from the usual origins (`lib.js` ALLOWED_ORIGINS).

Error responses: `403 {"ok":false,"error":"bad-admin-key"}`, `404 {"ok":false,"error":"unknown-ops-route","routes":[…]}`, `500 {"ok":false,"error":"ops-failed","why":"…"}`.

Never put the key in a URL query string.

## Endpoints

| Method | Path | What |
|---|---|---|
| GET | `/api/ops/realtime` | WhatsApp per number, cap, what the next pacer tick will do, calls today, Noa, last pacer tick |
| GET | `/api/ops/capacity?days=14` | 14-day planner: planned vs capacity, overflow, recommendations |
| GET | `/api/ops/balances?fresh=1` | vendor balances (10 min cache) |
| POST | `/api/ops/balances` | `{set:{vendor, amount, currency, auto_topup}}` stores a manual balance |
| GET | `/api/ops/registry` | registry nodes, ops metadata and runtime state |
| GET | `/api/ops/code?id=<node>` | source of the function behind a node |
| POST | `/api/ops/toggle` | `{id, enabled, confirm?, reason?, who?}`: blast radius, then the write once confirmed |
| GET | `/api/ops/live?since=<ms>&limit=200` | newest audit and ledger rows (poll every 3 s) |
| GET | `/api/ops/runs?automation_id=&status=&from=&to=&cursor=&limit=50` | ledger list |
| GET | `/api/ops/run?id=<run id>&token=<event token>` | one run, its children, and linked audit rows |

### GET /api/ops/realtime

Read-only. The only possible write is the `wa:cap` tier cache, which `waCapInfo` refills when it has expired, exactly as `/api/cap-status` does today.

- `wa.numbers[]`: one row per guest number (`role:"guests"`) plus Noa 4499 (`role:"client"`). Fields:
  - `tier`, `quality`, `limit`, `used_24h`, `remaining`, `held`, `held_until`, `frees_at` come from `guestCapacity` (budget.js). They are `null` for the client number.
  - `sent_today` and `rejected_today` count today's `wa_out` audit rows for this number (Israel day). `ok:true` means sent; `ok:false` means Meta refused the request.
  - `failed_async_today` counts `wa_status` rows with status `failed`, joined to this number by wamid.
  - `failed_by_code` is keyed by Meta error code and covers both refusals and async failures.
  - `by_reason` uses the reasons in `wa.reasons`: `wave · daybefore · eventday · table · thanks · gift · subevent · client · reply · manual`. `reply` is free text. `client` is a client template from 4499. `manual` is anything else, including SMS (SMS is not counted on any WhatsApp number).
  - `by_event` is keyed by the first 8 characters of the event token (`—` when there is no token), as `{ total, <reason>: n }`.
- `wa.unknown_numbers[]`: phone ids seen in the audit log that are not configured.
- `cap`: the shared budget from `guestCapacity` (`scope` is `portfolio` or `number`) plus `wacap_guests` (the global stop timestamp, or `null`).
- `queue`: what the next tick (`next_tick_at`) will do, and why.
  - `sends.why`: `will-send · paused · off:d_pacer · <window reason> · nothing-pending · cap · wacap:guests`. `sends.max` = min(25, cap.remaining).
  - `calls.why`: `will-dial · paused · off:d_pacer · <window reason>`. The first `callbacks` (up to 3) are taken out of the 6 dials.
  - `autoretry`: whether the daily retry will run this tick.
  - Also: `event_day_due[]` (tok8), `late_invites_waiting`, `holds`.
- `calls`: Retell calls that started today. `null` when `RETELL_KEY` is missing.
  - `dialed`, `answered`, `voicemail`, `no_answer`, `in_progress` (outbound only), `inbound`, `cost_usd`.
  - `queued` = the "נדרשת שיחה" queue minus guests who reached their try cap.
  - `capacity_left_today` = ticks left with the window open × 6. `remaining_today` = min(queued, capacity).
  - `by_event[tok8]`, `callbacks_queued`.
  - `source`: `retell`, or `retell-unreadable` when the list call failed.
- `noa`: `billing_131042` is the 6-hour `billingalert:client` flag. `last_send` is the newest `wa_out` from 4499, with the phone masked.
- `pacer`: `last_tick_at` and a summary taken from `pacer:last`, plus `off` (the kill switch) and `paused`.
- `audit_until_ts`: the newest audit row counted. `scripts/ops-check-realtime.mjs` compares only rows up to it.

### GET /api/ops/capacity

A read-only projection: it never runs the engine (the engine's dry path writes KV, see automations.js). The only write is the `biz:verif` cache (6 h).

- `model`:
  - Business not verified (`verification.status` from Graph `GET /1378764257421712?fields=business_verification_status`, cached in `biz:verif`): `model:"shared"`, `capacity_per_day` = portfolio limit − margin (250 − 20 = 230).
  - Verified: `model:"per_number"`, each number's tier with a floor of 1000, summed.
  - `today_remaining` = `guestCapacity().remaining`. Later days get the full capacity.
- `days[]` covers the horizon:
  - `open` is false on Shabbat and no-contact days; capacity is 0 on those days.
  - `planned` excludes held events. Held events are counted in `held_planned` and flagged `held:true` in `by_event`.
  - `overflow` = planned − capacity, never below 0.
  - `by_event[].type` is one of `w1 w2 w3 daybefore table eventday thanks subevent`. `upper_bound:true` means per-guest sent markers were not read, so the real number can be lower.
- `recommendations[]`: events are processed in order of first due day, then token, and claim free capacity greedily. The result is deterministic.
  - `kind:"fits"`: the batch fits on its due day.
  - `kind:"move"`: `day` is the earliest day that fits the whole batch.
  - `kind:"no_window"`: the batch fits a single day's capacity but no day in the horizon has room left.
  - `kind:"split"`: the batch is bigger than one day's capacity. Includes `days_needed`, `split[{day,count}]`, `unplaced` and `needs_capacity_by`, and the `he` text explains verification (an extra number only helps after verification).
- Sub-events (שבת חתן) are sent manually and have no date, so their unsent remainder is planned for today with `manual:true`.

#### `rolled` (03/11)

Each `days[]` row also carries the plan as it will actually leave:
- `rolled[]`: `{tok8, token, event, type, type_he, n, from_day}`. What goes out that day. `from_day < day` means the item was due earlier and the planner moved it here.
- `out` = sum of `rolled[].n` (always ≤ `capacity`). `rolled_in` = the moved part of `out`. `carry` = what is still waiting at the end of that day.
- Top level: `unplaced[]` (does not fit inside the horizon) and `totals.out`, `totals.unplaced`.

Rules: FIFO by due day, then token and type, same order as the recommendations. Held items never roll. Closed days (Shabbat, no-contact list) have capacity 0, so nothing lands on them. Friday holds at most `model.friday_capacity`. That value is 25 pacer ticks in the 09:00–13:00 window × `PACE_SENDS` (25) = 625, so with the shared 230 cap Friday is a full 230 today. It becomes the binding limit only when the cap rises above 625. Today's room is `today_remaining`.

Test fixture (worker/test/ops-capacity.test.mjs): 176 due Tuesday with 68 room, 507 due Wednesday, `friday_capacity` 100 → Tue 68 · Wed 230 = 108 (↪ Tue) + 122 · Thu 230 · Fri 100 · Shabbat 0 · Sun 55 (the rest).

### GET /api/ops/calendar?month=YYYY-MM

Read-only. `month` is a POST body or query param and defaults to the current Israel month. `fresh=1` skips the 5-minute `opscal:<month>` KV cache, which is the only write. Sources merged per Israel day:

| Source | Gives |
|---|---|
| snapshot (eventsFromRaw, from month start − 30 d) | `days[].events[]` `{tok8, name, type (occasion), time (reception)}` |
| `sendBoardData()` (the /api/send-board board, its 5-min cache) | per event × type: audience, sent, pending (hold / scheduled), last_at, sub-events |
| `buildCapacity(horizon to month end, ≤ 28 d)` | `rolled` → `planned` / `rolled` + `ghost` chips, held from `by_event` |
| audit `wa_out` + `wa_status` (month days ≤ today, budget 1500 ops each) | per day × event × type: sent / delivered / failed + the template seen → `done` / `partial` chips, `used` |
| audit `call` (agent שיר) | `call` chips done: n, answered |
| `buildCallQueue(snapshot)` | `call` chip planned: guests not capped, on the next open call day |
| audit `pay` (Grow IPN), only rows `parsePaidDesc` recognises as an ishur package, deduped by asmachta | `closed` items: event (matched by client id C-<phone9>, else payer name), package, records, sum |

`state`: `done` (all sent, or nothing pending) · `partial` (audit or board saw sends but non-held pending remains; `completion_day` = the last rolled day for that event × type) · `planned` · `held` (on the due day, or today if overdue) · `rolled` (on the day it goes out, `from_day`) · `ghost` (one per original day, `to_days[]`, `n` = total moved). `closed_reason`: `shabbat` | `no_contact` | null. `limited: "friday"`. `used` = audit sends (past and today) + rolled `out` (today and future). Today's `capacity` = used + remaining.

Known limits: past chips older than the audit window come from the board's KV markers (one chip on `last_at`'s day, reason says so). Board types are only for events from today − 2 days on. The call-round plan is a count of guests in Shir's queue, not a dial schedule.

Until then it composes the month locally with the real `planCapacity` + `calendarMonth` over live `/api/ops/capacity` + `/api/send-board`. That version has no audit counts, closed purchases or Shir rounds (flagged in `source`). The same script adds `rolled` to fixtures/ops/capacity.json by re-planning that fixture's own items.

### GET /api/ops/balances · POST /api/ops/balances

Every vendor returns the same shape: `{vendor, amount, currency, source:'api'|'manual', checked_at, dashboard_url, topup_url, auto_topup:'on'|'off'|'unknown', status:'ok'|'low'|'error', low_threshold, error, extra}`.
`status` is `low` when `amount < low_threshold`. Thresholds live in `BALANCE_LOW` in `automations-registry.js`.
The whole answer is cached for 10 minutes in KV `bal:cache`; `?fresh=1` skips the cache. Manual values live in KV `bal:manual:<vendor>` as `{amount, currency, auto_topup, at}`, and `extra.stale_days` says how old a manual value is.

| vendor | source | amount means |
|---|---|---|
| `telnyx` | API `GET https://api.telnyx.com/v2/balance` (`TELNYX_KEY`) | available credit (falls back to balance), USD |
| `cloudflare` | API GraphQL `workersInvocationsAdaptive` when `CF_API_TOKEN` and `CF_ACCOUNT_ID` are set, otherwise manual | Worker requests this month (`currency:"requests_mtd"`). Cloudflare has no prepaid balance. |
| `meta_ads` | API `act_1944903292858482?fields=balance,amount_spent,spend_cap,currency,…` (`META_ADS_TOKEN`) | spend_cap − amount_spent (`null` when no cap is set). `extra.balance_owed` = the unbilled balance. Money fields are converted from minor units. |
| `meta_wa` | API `GET /<waba>?fields=pricing_analytics.start().end().granularity(DAILY)` for both WABAs (guests: `WA_TOKEN_GUESTS`; client: `clientToken`) | spend this month, USD. This is spend, not a balance; the payment method is not readable. |
| `retell` | manual. Retell has no balance endpoint (docs.retellai.com/accounts/billing, checked 03/11). | the manual value. `extra.concurrency` comes from `GET /get-concurrency`. `extra.billing_guard_tripped` reflects `billretell` and forces `status:"low"`. |
| `anthropic` | manual. The credit balance is not exposed by the API. | the manual value |

- `kill_switch` is `null` when the node has no switch of its own; then only the global `paused` key stops it. `wave_retry` has `{key:"auto:off:manual_blasts", wired:true, via:"manual_blasts"}`.
- `state.enabled` is always `true` for nodes without a switch. `state.off` = `{at, by, reason}` while the switch is off.
- `side_effects` vocabulary: `wa_guest wa_client call sms email sheet kv monday slack money meta`. `risk` is one of `high medium low`.

### POST /api/ops/toggle

Body: `{admin_key, id, enabled: boolean, confirm?: string, reason?: string, who?: string}`.

1. A call without `confirm` (or with a wrong one) writes nothing. It returns the blast radius (when turning a switch off) and `applied:false`, `confirm_required:"<switch id>"`.
2. A call with `confirm === <switch id>` (or the node id) writes or deletes KV `auto:off:<switch id>` as `{at, by, reason}`. It also writes an audit record (`kind:"admin"`, area `מרכז בקרה`) and posts one Slack line. The response has `applied:true`.

Blast radius:
- `downstream[]`: computed over `depends_on` edges (what runs a node). A node is `fully_stopped:false` when another parent still runs it; `other_parents` lists those parents. For example, the morning cron still runs `d_engine` when the pacer is off.
- `messages_next_days.total`: projected messages over the next 7 days whose node is fully stopped. `partial_total` counts messages whose node is only partly stopped.
- `calls_stopped`: the dial queue (for `shir_dispatch`) and the callback queue (for `shir_callbacks`).
- `events_affected[]`: the events those messages belong to.

Errors:
- 404 `unknown-id`
- 409 `no-kill-switch` (the code does not check a switch for this node; the response lists the ids that have one)
- 400 `enabled-must-be-boolean`
- 405 on GET

```json
{ "ok": true, "id": "wave1", "switch_id": "wave1", "key": "auto:off:wave1", "enabled_now": true, "requested_enabled": false, "off_since": null,
  "blast_radius": { "id": "wave1", "downstream": [], "messages_next_days": { "total": 9, "by_type": { "w1": 9 }, "partial_total": 0 },
    "calls_stopped": { "queued": 0, "callbacks": 0 },
    "events_affected": [{ "token": "c1c5fcf5-0000-4000-8000-0000000000aa", "tok8": "c1c5fcf5", "name": "אורי ויצחק", "messages": 9, "days": ["2026-11-04"] }], "horizon_days": 7 },
  "confirm_required": "wave1", "applied": false, "he": "כדי לבצע, לשלוח שוב עם confirm: \"wave1\"" }
```

What each switch does in code (`isOff(env, id)`, one KV get, fails open on a KV error):

| switch | where it is checked | effect while off |
|---|---|---|
| `d_pacer` | `runPacer`, first line | the whole tick is skipped: no Slack flush, sends, dials, doctor or `pacer:last`. Returns `{skipped:'off:d_pacer'}`. |

## The runs ledger

`withRun(env, automation_id, fn, {triggered_by, parent, job})` in `worker/ops-run.js`:
- It wraps every `scheduled()` job (each former `audit.job` call goes through `opsJob`, which maps the job name to a registry id with `JOB_TO_ID`). It also wraps the morning engine, the backup, the Monday digest, the morning undelivered list and the 04:00 heartbeat.
- Inside the pacer, each sub-step is a child run: `d_engine`, `lead_chase`, `reconcile_calls`, `shir_callbacks`, `shir_dispatch`, `noa_lead_dial`, `template_check`, `doctor`. The daily retry is reported in the pacer's summary, not as a child run.
- These manual routes get one run each (`triggered_by:"manual"`): `/api/gift-blast` and `/api/subevent-send` (as `manual_blasts`), `/api/daily-run` (as `d_engine`), `/api/shir-dispatch` (as `shir_dispatch`).
- The audit.js cron row is kept, so live.html and automations.html are unchanged, and it now carries `data.run_id` and `data.automation_id`.
- Storage is D1 `OPS_DB` (an insert at start, an update at end). If the binding is missing or D1 throws, a finished run is written to the KV ring `opsrun:<inverted ms>:<id>` (TTL 3 days). The ledger never throws into the job.
